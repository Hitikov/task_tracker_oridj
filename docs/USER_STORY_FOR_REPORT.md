# User Stories (подробные) — Arij

## US-01. Создание задачи в проекте

**Формулировка:**
> **Как** руководитель проекта,
> **я хочу** создавать задачу с названием, описанием, типом, приоритетом, исполнителем и дедлайном,
> **чтобы** фиксировать работу команды в системе и распределять ответственность.

**Связанные требования:**
- FR: M-08 (создание задачи), M-12 (автономер), M-13 (основные поля), M-14 (исполнитель), M-17 (иерархия Epic → Task → Subtask), M-25 (валидация), M-26 (обработка ошибок), M-24 (контроль доступа).
- NFR: N-01 (REST API), N-02 (JWT), N-04 (хранение в БД).

**Исходные условия:**
- Пользователь аутентифицирован (валидный JWT).
- Пользователь имеет доступ к проекту и права на создание задач.
- В проекте существует хотя бы один участник, которому можно назначить задачу.
- Пользователь находится на странице создания задачи в выбранном проекте.

**Уточнения (согласованные правила поведения):**
- Обязательное поле — только **название**; описание, тип, приоритет, исполнитель и дедлайн — необязательны (задача создаётся и без них).
- Номер задачи присваивается автоматически и уникален в рамках проекта (например, `ARIJ-42`).
- Тип задачи по умолчанию — `Task`; допустимые значения из справочника `TaskType` (Epic, Task, Subtask, Bug, Feature).
- Родительский элемент (Epic для Task, Task для Subtask) задаётся опционально; при указании родителя система проверяет его существование и принадлежность тому же проекту.
- Исполнитель выбирается только из участников проекта (`ProjectMember`).
- Дедлайн задаётся датой; прошедшая дата допускается, но помечается как просроченная.
- После успешного создания задача сразу появляется в Backlog проекта.

**Критерии приёмки:**

*Основной успешный сценарий (Дано – Когда – Тогда):*
> **Дано:** пользователь с правами на создание задач открыл форму создания задачи в проекте.
> **Когда:** он заполняет название «Падает сессия при логауте», выбирает тип `Bug`, приоритет `High`, исполнителя «Иван», дедлайн и нажимает «Сохранить».
> **Тогда:** задача создаётся, ей присваивается уникальный номер, она отображается в Backlog проекта с указанными атрибутами.

*Граничный / отрицательный сценарий:*
> **Дано:** пользователь открыл форму создания задачи.
> **Когда:** он оставляет поле «Название» пустым и нажимает «Сохранить».
> **Тогда:** задача не создаётся, отображается сообщение об ошибке валидации, форма остаётся открытой с введёнными данными.

*Дополнительные проверяемые условия:*
1. Повторное нажатие «Сохранить» при уже созданной задаче не создаёт дубликат (защита от повторной отправки).
2. Если выбранный исполнитель не является участником проекта, система отклоняет создание с сообщением об ошибке.
3. Задача сохраняется в PostgreSQL и доступна после перезапуска клиента и повторного входа.

**Открытые вопросы и зависимости:**
- Зависит от US «Регистрация/Авторизация» (нужен аутентифицированный пользователь) и «Создание проекта» + «Добавление участника» (нужен проект и исполнитель).
- Открытый вопрос: нужна ли проверка на дубликат названия при создании (сейчас вынесено в Post-MVP как AI-функция — подтвердить, что в MVP дубликаты не блокируются).

## US-02. Просмотр задач в Backlog

**Формулировка:**
> **Как** руководитель проекта,
> **я хочу** видеть все задачи проекта списком в Backlog с названием, статусом, дедлайном, исполнителем и приоритетом,
> **чтобы** понимать, что запланировано, и расставлять приоритеты работы команды.

**Связанные требования:**
- FR: M-18 (Backlog), M-11 (просмотр задачи), M-24 (контроль доступа), M-26 (обработка ошибок).
- NFR: N-01 (REST API), N-02 (JWT), N-04 (хранение в БД).
- Связанные Should: S-03 (сортировка Backlog), S-05 (фильтрация) — не входят в MVP, история от них не зависит.

**Исходные условия:**
- Пользователь аутентифицирован.
- Пользователь имеет доступ к проекту (участник проекта или владелец).
- В проекте есть хотя бы одна задача (для проверки пустого состояния — может не быть).
- Пользователь открыл представление Backlog выбранного проекта.

**Уточнения (согласованные правила поведения):**
- Отображаются только задачи выбранного проекта, к которому у пользователя есть доступ.
- Для каждой задачи видны: название, статус, дедлайн, исполнитель, приоритет.
- Если поле не заполнено (например, нет исполнителя или дедлайна), оно отображается как «—» / «Не назначен», без ошибки.
- При отсутствии задач отображается пустое состояние с пояснением, а не ошибка.
- Сортировка по полям — в MVP опциональна (S-03); базовый порядок — по номеру задачи.
- Изменение данных другим пользователем не обязано отображаться в реальном времени (real-time — S-13, вне MVP).

**Критерии приёмки:**

*Основной успешный сценарий:*
> **Дано:** в проекте есть задачи с разными статусами, исполнителями и приоритетами; пользователь имеет доступ к проекту.
> **Когда:** пользователь открывает представление Backlog.
> **Тогда:** отображается список задач проекта; для каждой задачи видны название, статус, дедлайн, исполнитель и приоритет.

*Граничный / отрицательный сценарий:*
> **Дано:** пользователь не является участником проекта (нет доступа).
> **Когда:** он пытается открыть Backlog этого проекта (например, по прямой ссылке).
> **Тогда:** задачи проекта не отображаются, система сообщает об отсутствии доступа.

*Дополнительные проверяемые условия:*
1. Если в проекте нет задач, Backlog отображается в пустом состоянии без ошибки.
2. Задача без исполнителя и без дедлайна отображается корректно (поля-заглушки), список не ломается.
3. Задачи другого проекта в Backlog не попадают.

**Открытые вопросы и зависимости:**
- Зависит от US-01 (создание задачи) — иначе нечего отображать.
- Зависит от «Создание проекта» и «Добавление участника».
- Открытый вопрос: нужна ли в MVP сортировка/фильтрация в Backlog (сейчас S-03/S-05 — Should, вне обязательного состава; подтвердить с преподавателем, что базовая история принимается без них).

## US-03. Изменение статуса задачи через Kanban

**Формулировка:**
> **Как** исполнитель задачи,
> **я хочу** менять статус своей задачи, перемещая её карточку между колонками Kanban («To Do» → «In Progress» → «Done»),
> **чтобы** мой прогресс был виден команде без дополнительных отчётов.

**Связанные требования:**
- FR: M-15 (изменение статуса), M-16 (базовый workflow To Do / In Progress / Done), M-19 (Kanban), M-20 (изменение статуса в Kanban), M-24 (контроль доступа), M-26 (обработка ошибок).
- NFR: N-01 (REST API), N-02 (JWT), N-04 (хранение в БД).
- Связанные Should: S-02 (Drag & Drop) — в MVP смена статуса возможна и без drag&drop (например, через меню карточки); real-time (S-13) вне MVP.

**Исходные условия:**
- Пользователь аутентифицирован и имеет право изменять статус задачи.
- Задача принадлежит проекту, доступному пользователю.
- В проекте настроен базовый workflow со статусами To Do / In Progress / Done.
- Пользователь открыл представление Kanban проекта.

**Уточнения (согласованные правила поведения):**
- Базовый workflow допускает переходы между статусами To Do ↔ In Progress ↔ Done в рамках настроенных правил.
- Смена статуса возможна как перетаскиванием (при реализации S-02), так и через действие на карточке (обязательный минимум MVP).
- При успешной смене статуса карточка отображается в новой колонке, изменение сохраняется в БД.
- При ошибке сохранения задачи статус не меняется, карточка возвращается в исходную колонку, пользователю показывается сообщение об ошибке.
- Изменение статуса фиксируется в истории (S-12 — Should; в MVP минимум — сохранение текущего статуса, история опциональна).
- Другие участники увидят изменение при следующей загрузке/обновлении доски (real-time не обязателен в MVP).

**Критерии приёмки:**

*Основной успешный сценарий:*
> **Дано:** у исполнителя есть задача в статусе «In Progress», открыта Kanban-доска проекта.
> **Когда:** он перемещает карточку задачи в колонку «Done».
> **Тогда:** статус задачи меняется на «Done», изменение сохраняется, карточка отображается в колонке «Done»; после повторного открытия доски статус остаётся «Done».

*Граничный / отрицательный сценарий:*
> **Дано:** задача находится в статусе «Done»; базовый workflow не предусматривает перехода «Done» → «In Progress» (если такое правило настроено) **или** у пользователя нет прав на изменение статуса.
> **Когда:** пользователь пытается переместить карточку в «In Progress».
> **Тогда:** статус задачи не меняется, карточка остаётся в исходной колонке, отображается сообщение о недопустимости перехода / отсутствии прав.

*Дополнительные проверяемые условия:*
1. При ошибке сохранения на сервере карточка возвращается в исходную колонку, статус в БД не меняется.
2. Повторное перемещение в тот же статус не создаёт ошибку и не дублирует задачу.
3. Смена статуса одной задачи не меняет статусы других задач на доске.

**Открытые вопросы и зависимости:**
- Зависит от US-01 (создание задачи) и «Создание проекта» + «Добавление участника».
- Открытый вопрос: входит ли Drag & Drop (S-02) в MVP или достаточно смены статуса через меню карточки — влияет на критерий приёмки и на объём ноября. Сейчас история сформулирована так, чтобы приниматься **без** drag&drop.
- Зависит от правил workflow: нужно подтвердить, что базовые статусы и переходы настраиваются на уровне проекта (M-16).
