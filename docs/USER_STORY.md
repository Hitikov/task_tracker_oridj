## 1. ИИ-агент: преобразование команды в JSON

**Как** тимлиду команды разработки,
**Я хочу** написать локальному ИИ-агенту команду в свободной форме
(«Создай баг в эпике Авторизация, назови "Падает сессия при логауте", приоритет высокий, исполнитель Иван»),
**Чтобы** агент преобразовал её в структурированный JSON с полями задачи.

### Критерии приёмки

- **Дано:** агент запущен и доступен.
- **Когда:** я отправляю команду в свободной форме.
- **Тогда:** агент возвращает JSON с полями: `тип`, `эпик`, `название`, `приоритет`, `исполнитель`.

---

## 2. ИИ-агент: создание задачи через API (MCP)

**Как** тимлиду команды разработки,
**Я хочу,** чтобы агент на основе JSON создавал задачу через API (MCP),
**Чтобы** не заполнять форму вручную.

### Критерии приёмки

- **Дано:** агент получил структурированный JSON.
- **Когда:** он вызывает API создания задачи.
- **Тогда:** задача создаётся в системе.

---

## 3. LLM: предупреждение о дубликате задачи

**Как** разработчику,
**Я хочу,** чтобы локальная LLM при вводе названия новой задачи сравнивала его с существующими
и при совпадении ≥ 80% показывала предупреждение с ID и названием похожей задачи,
**Чтобы** не создавать дубликаты.

### Критерии приёмки

**Сценарий 1 — предупреждение найдено:**

- **Дано:** в системе есть задача «Падает сессия при логауте» (ID-124).
- **Когда:** я ввожу название «Сессия падает при выходе».
- **Тогда:** система показывает предупреждение: «Похоже, задача с такой проблемой уже существует (ID-124)» с кнопками «Перейти» и «Всё равно создать».

**Сценарий 2 — принудительное создание:**

- **Дано:** система показала предупреждение.
- **Когда:** я нажимаю «Всё равно создать».
- **Тогда:** задача создаётся без повторного предупреждения.

## 4. Создание задачи

**Как** руководителю проекта,
**Я хочу** создавать задачу с названием, описанием, дедлайном и исполнителем,
**Чтобы** фиксировать работу команды в системе.

### Критерии приёмки

- **Дано:** я на странице создания задачи.
- **Когда:** я заполняю название, описание, дедлайн и исполнителя и нажимаю «Сохранить».
- **Тогда:** задача создаётся, ей присваивается уникальный номер, она появляется в бэклоге.

---

## 5. Просмотр задач в бэклоге

**Как** руководителю проекта,
**Я хочу** видеть все задачи проекта в виде списка в бэклоге,
**Чтобы** понимать, что запланировано.

### Критерии приёмки

- **Дано:** в проекте есть задачи.
- **Когда:** я открываю бэклог.
- **Тогда:** отображается список задач с полями: название, статус, дедлайн, исполнитель, приоритет; доступна сортировка по каждому полю.

---

## 6. Kanban-доска для исполнителя

**Как** исполнителю,
**Я хочу** видеть свои задачи на Kanban-доске и перетаскивать их между колонками статусов
(«В работе» → «На ревью» → «Готово»),
**Чтобы** мой прогресс был виден всей команде без дополнительных отчётов.

### Критерии приёмки

- **Дано:** у меня есть задачи со статусом «В работе».
- **Когда:** я перетаскиваю карточку в колонку «На ревью».
- **Тогда:** статус задачи меняется на «На ревью», изменения сохраняются, другие участники видят обновление.

---

## 7. Reports: круговая диаграмма по статусу

**Как** руководителю проекта,
**Я хочу** видеть круговую диаграмму распределения задач по статусу,
**Чтобы** понимать, сколько задач на каждом этапе.

### Критерии приёмки

- **Дано:** в проекте есть задачи с разными статусами.
- **Когда:** я открываю Reports.
- **Тогда:** отображается круговая диаграмма с долями по каждому статусу и легендой.
