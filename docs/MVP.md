## 1. Цель документа

Данный документ определяет границы MVP (Minimum Viable Product) проекта Arij на период одного семестра — с сентября по декабрь.

Для определения приоритетов используется метод MoSCoW:

- **M — Must have** — обязательная функциональность;
- **S — Should have** — важная функциональность, которую желательно реализовать;
- **C — Could have** — дополнительные функции, которые можно сделать при наличии времени;
- **W — Won't have** — функции, которые не входят в текущий MVP и переносятся на следующие версии.

---

## 2. Граница MVP

Arij — кроссплатформенное приложение для командного управления проектами и задачами.

Основная задача MVP — дать команде возможность работать с проектом в одном месте: создавать задачи, назначать исполнителей, менять статусы и отслеживать общий прогресс.

Основной сценарий работы с MVP:

1. Пользователь регистрируется и входит в систему.
2. Создаёт проект.
3. Добавляет участников команды.
4. Создаёт Epic, Task или Subtask.
5. Назначает исполнителя.
6. Устанавливает приоритет, дедлайн и статус.
7. Просматривает задачи в Backlog и Kanban.
8. Меняет статус задачи по мере выполнения.

Таким образом, основой MVP является не количество представлений и дополнительных функций, а рабочий цикл управления задачами внутри команды.

# 3. MoSCoW

## 3.1. M — Must have

Must have — функции, которые считаются обязательными для MVP. Если какая-то из них отсутствует, основной сценарий работы Arij не будет полностью работать.

## Функциональные требования

| ID | Функциональность | Описание |
|---|---|---|
| M-01 | Регистрация | Создание пользовательского аккаунта |
| M-02 | Авторизация | Вход пользователя в систему |
| M-03 | Выход | Завершение пользовательской сессии |
| M-04 | Пользователь | Хранение имени/логина и основных данных пользователя |
| M-05 | Создание проекта | Создание нового проекта |
| M-06 | Список проектов | Просмотр проектов, доступных пользователю |
| M-07 | Участники проекта | Добавление пользователей в проект |
| M-08 | Создание задачи | Создание новой задачи |
| M-09 | Редактирование задачи | Изменение параметров задачи |
| M-10 | Удаление задачи | Удаление задачи |
| M-11 | Просмотр задачи | Просмотр информации о задаче |
| M-12 | Номер задачи | Автоматическое присвоение номера задаче |
| M-13 | Основные поля задачи | Название, описание, тип, приоритет, исполнитель и дедлайн |
| M-14 | Исполнитель | Назначение задачи участнику проекта |
| M-15 | Статус | Изменение текущего статуса задачи |
| M-16 | Базовый workflow | Поддержка минимальных статусов: To Do, In Progress, Done |
| M-17 | Иерархия задач | Поддержка структуры Epic → Task → Subtask |
| M-18 | Backlog | Отображение списка задач проекта |
| M-19 | Kanban | Отображение задач по статусам |
| M-20 | Изменение статуса в Kanban | Возможность менять статус задачи через Kanban |
| M-24 | Контроль доступа | Ограничение доступа пользователей к проектам и задачам |
| M-25 | Валидация | Проверка обязательных и некорректных данных |
| M-26 | Обработка ошибок | Обработка основных ошибок клиента и сервера |


## Нефункциональные требования

| ID | Требование | Описание |
|---|---|---|
| N-01 | Архитектура взаимодействия | Клиент и сервер должны взаимодействовать посредством REST API |
| N-02 | Аутентификация | Для аутентификации запросов должен использоваться JWT |
| N-03 | Клиентское приложение | Клиентская часть системы должна быть реализована на Flutter |
| N-04 | Хранение данных | Данные пользователей, проектов, задач и связей между ними должны храниться в базе данных |

Основной критерий для Must have — пользователь должен иметь возможность пройти весь основной сценарий от регистрации до изменения статуса задачи.

## 3.2. S — Should have

Should have — функции, которые желательно реализовать в рамках семестра. Они делают Arij удобнее, но без них основной сценарий всё равно может работать.

| ID | Функциональность | Описание |
|---|---|---|
| S-01 | Приоритеты | Например: Low, Medium, High, Critical |
| S-02 | Drag & Drop Kanban | Перемещение задач между статусами |
| S-03 | Сортировка Backlog | Изменение порядка задач |
| S-04 | Поиск | Поиск задач по названию и другим параметрам |
| S-05 | Фильтрация | Фильтрация по статусу, исполнителю, приоритету и типу |
| S-06 | Calendar | Отображение задач по дедлайнам |
| S-07 | List/Table view | Табличное представление задач |
| S-08 | Сортировка таблицы | Сортировка по основным полям |
| S-09 | Цветовая индикация Epic | Визуальное выделение задач одного Epic |
| S-10 | Настраиваемые типы задач | Например Task, Bug, Feature, Epic |
| S-11 | Базовые роли | Например руководитель проекта и исполнитель |
| S-12 | История изменений | Просмотр основных изменений задачи |

## 3.3. C — Could have

Could have — дополнительные функции. Их стоит делать только после завершения основных функций MVP.

| ID | Функциональность | Описание |
|---|---|---|
| C-01 | Reports | Статистика и отчёты по проекту |
| C-02 | Timeline | Временная шкала проекта и задач |
| C-03 | Расширенная аналитика | Среднее время выполнения, распределение задач и другие метрики |
| C-04 | Гибкий workflow | Создание собственных статусов и переходов |
| C-05 | Пользовательские поля | Дополнительные поля для задач |
| C-06 | Расширенная ролевая модель | Admin, Manager, Developer, Viewer |
| C-07 | Уведомления | Уведомления об изменениях и назначении задач |
| C-08 | Комментарии | Обсуждение задач внутри проекта |
| C-09 | Вложения | Добавление файлов и изображений к задачам |
| C-10 | Тёмная тема | Дополнительная настройка интерфейса |

---

## 3.4. W — Won't have

Won't have — функции, которые не планируется включать в MVP текущего семестра. В дальнейшем они могут появиться в следующих версиях проекта.

| ID | Функциональность | Причина переноса |
|---|---|---|
| W-01 | AI-агент | Отдельный большой функциональный блок |
| W-02 | Создание задач через AI | Требует интеграции LLM и MCP |
| W-03 | Редактирование задач через AI | Требует интеграции агента с API |
| W-04 | Получение статистики через AI | Требует готовой аналитической подсистемы |
| W-05 | Свободное общение с AI-агентом | Не относится к основному сценарию MVP |
| W-06 | Полноценная мобильная версия | Увеличивает объём разработки и тестирования |
| W-07 | Одновременная оптимизация Web, Desktop и Mobile | Слишком большой объём для одного семестра |
| W-08 | Сложная система разрешений | Можно реализовать после базовой версии |
| W-09 | Продвинутая аналитика | Не является обязательной для первой версии |
| W-10 | Сложные кастомные workflow | Можно добавить после базовой реализации |
| W-11 | Интеграции с GitHub, GitLab, Slack и другими сервисами | Не нужны для проверки основной идеи |
| W-12 | Production-grade масштабирование | Не является основной целью учебного проекта |

# 4. План разработки на семестр

## Сентябрь — фундамент

### Цель

Создать основную архитектуру проекта и подготовить взаимодействие между клиентом, сервером и базой данных.

### Планируемая работа

- спроектировать базу данных;
- реализовать пользователей;
- реализовать проекты;
- реализовать участников проектов;
- реализовать основные сущности задач;
- добавить статусы и типы задач;
- настроить JWT-аутентификацию;
- сделать основные REST API endpoints;
- создать структуру Flutter-приложения;
- реализовать регистрацию и авторизацию;
- сделать базовую навигацию приложения.

### Результат

К концу сентября пользователь должен иметь возможность зарегистрироваться, войти в систему и создать проект.

---

## Октябрь — управление задачами

### Цель

Реализовать основную работу с задачами и командами.

### Планируемая работа

- создание задач;
- просмотр задач;
- редактирование задач;
- удаление задач;
- назначение исполнителя;
- установка приоритета;
- установка дедлайна;
- изменение статуса;
- реализация Epic, Task и Subtask;
- добавление участников проекта.

### Дополнительно

Если основная часть готова, можно начать:

- базовые роли;
- историю изменений;
- Drag & Drop.

### Результат

К концу октября команда должна иметь возможность вести проект и работать с задачами.

---

## Ноябрь — визуализация

### Цель

Сделать работу с задачами более удобной и наглядной.

### Основная работа

- реализовать Kanban;
- реализовать Backlog;
- отображать исполнителя;
- отображать приоритет;
- отображать дедлайн;
- сделать изменение статуса через Kanban.

### При наличии времени

Можно добавить:

- поиск;
- фильтрацию;
- сортировку;
- Calendar;
- List/Table view;
- цветовую индикацию Epic.

### Результат

Пользователь может удобно просматривать и изменять состояние задач через интерфейс приложения.

---

## Декабрь — стабилизация и завершение MVP

### Цель

Закончить основную разработку, исправить ошибки и подготовить проект к демонстрации.

### Планируемая работа

- исправление критических ошибок;
- обработка ошибок;
- проверка валидации;
- проверка прав доступа;
- тестирование REST API;
- тестирование основных пользовательских сценариев;
- интеграция frontend и backend;
- подготовка документации;
- подготовка демонстрации проекта.

Если основная функциональность уже работает стабильно, можно добавить отдельные функции из Should have или Could have, например Reports, Timeline, комментарии или уведомления.

Главный приоритет декабря — не добавление новых функций, а стабильность уже реализованного MVP.

# 5. Основные сущности MVP

Для первой версии достаточно реализовать следующие основные сущности:

- `User` — пользователь;
- `Project` — проект;
- `ProjectMember` — участник проекта;
- `Task` — задача;
- `TaskType` — тип задачи;
- `Status` — статус задачи.

Для иерархии задач можно использовать связь между задачами, например:

`Epic → Task → Subtask`

Также задачи должны быть связаны с проектом и исполнителем.

# 6. AI как Post-MVP

AI является одной из запланированных возможностей Arij, но для текущего MVP его лучше оставить за пределами основной версии.

В будущем AI-агент сможет:

- создавать задачи через естественный язык;
- редактировать задачи;
- менять статусы;
- получать статистику по проекту;
- отвечать на вопросы по задачам;
- взаимодействовать с API через MCP.

Предполагаемая архитектура:

`Flutter → REST API / MCP → AI Agent → Gemma → Arij API → PostgreSQL`

Сначала необходимо сделать стабильными базу данных и REST API. После этого интеграция AI будет проще, поскольку агент сможет использовать уже готовые операции системы.

# 7. Критерии готовности MVP

MVP можно считать готовым, когда реализован основной сценарий работы пользователя:

1. Пользователь может зарегистрироваться.
2. Пользователь может войти в систему.
3. Пользователь может создать проект.
4. Пользователь может добавить участников.
5. Пользователь может создать задачу.
6. Задача получает уникальный номер.
7. Можно назначить исполнителя.
8. Можно установить приоритет.
9. Можно установить дедлайн.
10. Можно изменить статус.
11. Поддерживается структура Epic → Task → Subtask.
12. Задачи отображаются в Backlog.
13. Задачи отображаются на Kanban.
14. Изменения сохраняются в PostgreSQL.
15. Клиент взаимодействует с сервером через REST API.
16. Для аутентификации используется JWT.
17. Реализован базовый контроль доступа.
18. Основной сценарий работает от начала до конца.
19. Критические ошибки исправлены.
20. Основной функционал протестирован.

# 8. Итоговый scope MVP

Для первого семестра основной функционал Arij можно разделить следующим образом:

### Must have

Авторизация, пользователи, проекты, участники, задачи, Epic/Task/Subtask, статусы, исполнители, приоритеты, дедлайны, Backlog, Kanban, REST API, PostgreSQL, JWT и базовый контроль доступа.

### Should have

Поиск, фильтрация, сортировка, Calendar, List/Table view, Drag & Drop, базовые роли, история изменений и дополнительные настройки задач.

### Could have

Reports, Timeline, расширенная аналитика, комментарии, уведомления, вложения, пользовательские поля и более сложная настройка workflow.

### Won't have

AI-агент, интеграция с LLM через MCP, полноценная мобильная версия, внешние интеграции и сложная система разрешений.

Такой scope позволяет за один семестр сделать не просто набор отдельных экранов, а законченный основной сценарий командного трекера задач. Дополнительные функции можно постепенно добавлять после того, как базовая версия будет стабильной.
