# ADR-0001: серверный стек Arij

- **Статус:** accepted
- **Дата:** 2026-11-21
- **Этап:** 0, поток 2 (ADR + OpenAPI)
- **Связанные документы:** [ROADMAP](../ROADMAP.md), [OpenAPI](../api/openapi.yaml), [Архитектура](../architecture.md)

## Контекст

Arij — кроссплатформенный трекер задач. Клиент написан на Flutter и уже использует
Drift поверх SQLite для локального хранения данных (демо-CRUD над `Person`).
Серверной части в репозитории нет: каталог `server/` отсутствует, миграций и API нет.

При этом в клиентском `pubspec.yaml` уже объявлены `shelf`, `shelf_router` и `postgres`,
но код их не использует. В README в качестве персистентности указан `DORMql`.
Фактически это не зафиксированный стек, а набор неиспользуемых зависимостей и
упоминание в документации.

Ограничения и требования, влияющие на выбор:

- сервер должен быть на Dart 3.x, чтобы команда работала в одном языке и могла
  переиспользовать модели/утилиты;
- данные — в PostgreSQL, доступ по REST (`/api/v1`), аутентификация — JWT;
- контракт фиксируется до реализации (contract-first), схема БД — через миграции;
- локальная разработка и CI — через Docker Compose и PostgreSQL-сервис;
- срок MVP — 6 недель, поэтому важны зрелость библиотек и предсказуемость.

## Рассмотренные варианты

### Вариант A. `shelf` + `postgres` + SQL-миграции

HTTP-слой на `shelf`/`shelf_router`, доступ к PostgreSQL через низкоуровневый пакет
`postgres`, схема БД — обычные SQL-файлы, применяемые миграционным раннером.

**Плюсы**

- Оба пакета зрелые, широко используются и уже присутствуют в экосистеме проекта.
- Полный контроль над SQL: индексы, ограничения, `citext`, enum-типы, транзакции.
- SQL-миграции прозрачны, их легко проверить в CI на чистой БД и применять в Docker.
- Нет генерации кода и скрытой магии: поведение запросов предсказуемо.
- Сервер не зависит от клиентской схемы Drift; граница клиент/сервер остаётся явной.

**Минусы**

- Ручной маппинг строк результата в Dart-модели.
- Нет compile-time проверки запросов — ошибки в SQL ловятся тестами.
- Нужна дисциплина: параметризованные запросы, единый стиль миграций.

### Вариант B. `drift` + `drift_postgres`

Сервер использует Drift как ORM и `drift_postgres` как драйвер PostgreSQL.

**Плюсы**

- Типобезопасные запросы и генерация кода.
- Знакомый команде инструмент: Drift уже применяется на клиенте.
- Единый стиль описания таблиц в Dart.

**Минусы**

- `drift_postgres` — экспериментальный пакет с меньшим сообществом и меньшей
  предсказуемостью, чем связка `shelf` + `postgres`.
- DDL и миграции PostgreSQL всё равно требуют SQL; преимущество ORM частично теряется.
- Соблазн переиспользовать клиентскую схему размывает границу «локальный кэш / сервер».
- Дополнительный codegen (`build_runner`) в серверном CI и Docker-сборке.
- Риск блокирующих ограничений драйвера на enum-типы, `citext`, частичные индексы.

### Вариант C. `DORMql`

Ориентироваться на `DORMql`, упомянутый в README как средство персистентности.

**Плюсы**

- Соответствует текущей формулировке README.
- Потенциально более высокоуровневый интерфейс, если бы библиотека была зрелой.

**Минусы**

- В `pubspec.yaml` зависимости нет, в репозитории нет ни кода, ни конфигурации.
- Публичной документации, стабильной версии и подтверждённой поддержки, на которые
  можно опереться в срок MVP, найти не удалось.
- Риск заблокировать backend на неопределённом инструменте и переписывать слой БД.
- Несовместимо с требованием contract-first и прозрачными SQL-миграциями.

## Решение

Принят **вариант A: `shelf` + `shelf_router` + `postgres` + SQL-миграции**.

- Сервер — отдельный Dart-пакет `server/` с именем `arij_server`.
- HTTP: `shelf`, `shelf_router`; конфигурация: `dotenv`; логирование: `logging`.
- PostgreSQL: пакет `postgres`, пул соединений, параметризованные запросы.
- Схема БД: пронумерованные SQL-миграции, применяемые только вперёд.
- **Drift остаётся исключительно локальным кэшем Flutter-клиента.** Сервер не
  использует Drift, `drift_postgres` и клиентские таблицы.
- Аутентификация: JWT в заголовке `Authorization: Bearer <token>`, секрет —
  `JWT_SECRET` из env. Пароли хранятся только как **Argon2id- или bcrypt-хэш**;
  SHA-256, MD5 и открытый текст запрещены.
- `DORMql` из README считается устаревшим упоминанием; README будет обновлён
  отдельным потоком (гигиена репозитория), этот ADR фиксирует фактический стек.

Ссылки на контракт: [OpenAPI 3.1](../api/openapi.yaml), [архитектура](../architecture.md).

## Последствия

### Положительные

- Единый язык (Dart) на клиенте и сервере при явной границе через REST.
- Прозрачная схема БД и миграции, которые можно проверить на чистом PostgreSQL в CI.
- Зрелые зависимости и большое количество примеров снижают риск этапа 1.
- Клиентский Drift не влияет на серверную схему и может развиваться независимо.

### Отрицательные

- Больше ручного кода: SQL, маппинг строк, валидация на границе API.
- Ошибки в запросах выявляются тестами, а не компилятором.
- Нужно поддерживать собственный миграционный раннер и дисциплину именования.

### Что нужно сделать

1. Создать пакет `server/` с зависимостями `shelf`, `shelf_router`, `postgres`,
   `dotenv`, `logging`, `test` (поток 3 этапа 0).
2. Описать подключение к PostgreSQL через env-переменные `DB_*` и пул соединений.
3. Добавить SQL-миграции для `users`, `projects`, `project_members` на этапе 1;
   на этапе 2 — enum `task_kind`/`task_priority`/`user_role` и таблицы
   `task_types`, `statuses`, `tasks`.
4. Настроить применение миграций при старте (идемпотентно) и отдельную команду для CI.
5. Поднять PostgreSQL в Docker Compose и добавить сервис БД в backend CI.
6. На этапе 1 убрать неиспользуемые `shelf`, `shelf_router`, `postgres` из клиентского
   `pubspec.yaml` (изменение кода — вне зоны этого ADR).
7. Обновить README: заменить `DORMql` и `SHA-256` на фактический стек и
   Argon2id/bcrypt для паролей.

### Риски и меры

| Риск | Мера |
|---|---|
| SQL-инъекции при ручной сборке запросов | Только параметризованные запросы, запрет интерполяции пользовательских данных |
| Рассинхронизация схемы и кода | Миграции в репозитории, прогон всех миграций на чистой БД в CI |
| Утечка `JWT_SECRET` или пароля БД | Секреты только в env, `.env` не коммитится, `.env.example` без значений |
| Исчерпание пула соединений | Один пул на процесс, лимит из конфигурации, закрытие в тестах |
| Рост ручного маппинга | Выделить репозитории и общие модели, покрыть интеграционными тестами |
| Преждевременная оптимизация ORM | Вернуться к вопросу, если `drift_postgres` станет зрелым или вырастет сложность запросов |

## Пересмотр решения

ADR пересматривается, если:

- `drift_postgres` станет стабильным и появится требование типобезопасных запросов;
- объём SQL-кода станет критическим для поддержки;
- появятся требования к БД, несовместимые с выбранным пакетом `postgres`.

До этого стек считается зафиксированным для этапов 0–2.
