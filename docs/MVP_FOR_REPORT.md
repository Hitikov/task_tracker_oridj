## 1. Цель документа

Документ фиксирует границы MVP проекта Arij на период одного семестра
(сентябрь–декабрь) и распределяет пользовательские возможности по
категориям метода MoSCoW:

- **M — Must have** — обязательная функциональность; ядро MVP;
- **S — Should have** — важная функциональность, желательная в рамках семестра,
  но без неё основной сценарий работает;
- **C — Could have** — дополнительные функции при наличии времени;
- **W — Won't have** — осознанно исключённые из текущей версии возможности.

Приоритеты рассматриваются **в одном горизонте** — первая рабочая версия
к началу декабря. «Сейчас не делаем» означает «не делаем в этой версии»,
а не отказ от развития продукта.

## 2. Граница MVP

Arij — кроссплатформенное приложение для командного управления проектами
и задачами.

**Основная задача MVP** — дать команде возможность работать с проектом
в одном месте: создавать задачи, назначать исполнителей, менять статусы
и отслеживать общий прогресс через Backlog и Kanban.

**Основной пользовательский сценарий MVP (целостный результат):**

1. Пользователь регистрируется и входит в систему.
2. Создаёт проект и становится его участником.
3. Добавляет в проект участников команды.
4. Создаёт задачу (Epic / Task / Subtask) с названием, типом, приоритетом,
   исполнителем и дедлайном.
5. Видит задачи проекта в Backlog.
6. Меняет статус задачи через Kanban (To Do → In Progress → Done).
7. Изменения сохраняются в БД и доступны после повторного входа.

Таким образом, основой MVP является **рабочий цикл управления задачами
внутри команды**, а не количество представлений и дополнительных функций.

Обязательный состав MVP согласован с тремя подробными историями:
**US-01**, **US-02**, **US-03** (см. `docs/user-stories-detailed.md`).

## 3. MoSCoW

### 3.1. Must have

Must have — функции, без которых основной сценарий Arij не работает.
Каждый элемент проверен вопросом: «Если убрать эту возможность, сможет ли
пользователь всё ещё получить основной результат?» — ответ «нет».

| ID | Функциональность | Обоснование |
|---|---|---|
| M-01 | Регистрация | Без аккаунта пользователь не может войти и работать; вход в систему — стартовая точка основного сценария. |
| M-02 | Авторизация | Разграничение доступа к проектам и задачам невозможно без аутентификации; JWT-аутентификация опирается на вход. |
| M-03 | Выход | Завершение сессии — базовое требование безопасности на общих устройствах. |
| M-04 | Пользователь (профиль) | Все задачи и участники проекта привязаны к сущности `User`; без неё нельзя назначить исполнителя. |
| M-05 | Создание проекта | Проект — контейнер для задач; без него некуда добавлять задачи и участников. |
| M-06 | Список проектов | Пользователь должен попасть в свой проект, чтобы начать работу. |
| M-07 | Участники проекта | Исполнитель задачи выбирается только из участников; без этого нельзя назначить ответственного (US-01). |
| M-08 | Создание задачи | Ключевая операция MVP: без неё команде нечего планировать (US-01). |
| M-09 | Редактирование задачи | Задачи меняются в ходе работы; без правки полей MVP теряет актуальность. |
| M-10 | Удаление задачи | Ошибочно созданные задачи нужно убирать, иначе Backlog засоряется. |
| M-11 | Просмотр задачи | Детали задачи (описание, исполнитель, дедлайн) нужны для работы над ней. |
| M-12 | Автономер задачи | Уникальный номер — идентификатор задачи в команде; без него ссылки и обсуждения ломаются (US-01). |
| M-13 | Основные поля задачи | Название, описание, тип, приоритет, исполнитель, дедлайн — минимальный набор для постановки задачи (US-01). |
| M-14 | Исполнитель | Назначение ответственного — суть командной работы (US-01). |
| M-15 | Статус | Отслеживание прогресса невозможно без изменения статуса (US-03). |
| M-16 | Базовый workflow (To Do / In Progress / Done) | Минимальный набор статусов покрывает жизненный цикл задачи в MVP (US-03). |
| M-17 | Иерархия Epic → Task → Subtask | Крупные цели нужно дробить; без иерархии Backlog превращается в плоский список. |
| M-18 | Backlog | Основное представление для просмотра запланированных задач (US-02). |
| M-19 | Kanban | Наглядное представление задач по статусам — ядро контроля прогресса (US-03). |
| M-20 | Изменение статуса в Kanban | Без этого Kanban — только просмотр, а не инструмент работы (US-03). |
| M-24 | Контроль доступа | Доступ к проектам и задачам ограничен участниками; без этого MVP небезопасен и не соответствует N-02. |
| M-25 | Валидация | Некорректные данные (пустое название, чужой исполнитель) должны отклоняться — иначе БД засоряется (US-01, US-02). |
| M-26 | Обработка ошибок | Пользователь должен понимать, что пошло не так; при ошибке сохранения статус не меняется (US-01, US-03). |

#### Нефункциональные требования MVP

| ID | Требование | Как проверить |
|---|---|---|
| N-01 | Клиент и сервер взаимодействуют посредством REST API. | Проверить, что все операции MVP (регистрация, вход, создание проекта/задачи, смена статуса) выполняются через REST-эндпоинты; в DevTools/Postman видны соответствующие HTTP-запросы. |
| N-02 | Аутентификация запросов — JWT. | Запрос к защищённому эндпоинту без токена возвращает 401; с валидным токеном — 200; с истёкшим/поддельным — 401. |
| N-03 | Клиентская часть реализована на Flutter. | Проверить, что клиент собирается из единой кодовой базы Flutter (web/desktop) и запускается. |
| N-04 | Данные пользователей, проектов, задач и связей хранятся в БД. | Создать задачу, изменить статус, перезапустить клиент и сервер — данные сохраняются; проверить записи в PostgreSQL. |
| N-05 | Все сервисы (API, PostgreSQL, Nginx) разворачиваются в Docker-контейнерах через `docker-compose.yml`. | Выполнить `docker compose up` на чистой машине — система поднимается и доступна без ручной настройки. |
| N-06 | Nginx используется как веб-сервер и обратный прокси (раздача Flutter Web, проксирование REST API). | Открыть приложение по адресу Nginx; запросы `/api/*` проксируются на бэкенд; статика Flutter Web отдаётся Nginx. |

Основной критерий Must have: **пользователь проходит весь основной сценарий
от регистрации до изменения статуса задачи**, а изменения сохраняются.

### 3.2. Should have

Should have — важные функции, которые делают Arij удобнее, но без них
основной сценарий MVP работает. Это кандидаты на расширение после
получения основного результата.

| ID | Функциональность | Обоснование |
|---|---|---|
| S-01 | Приоритеты (Low/Medium/High/Critical) | Поле приоритета уже входит в M-13, но расширенная шкала и её использование в сортировке — улучшение; MVP работает и с базовым значением. |
| S-02 | Drag & Drop на Kanban | Удобная смена статуса; в MVP смена статуса возможна через действие на карточке (US-03), поэтому drag&drop — улучшение. |
| S-03 | Сортировка Backlog | Полезно для приоритизации, но US-02 принимается и с базовым порядком по номеру. |
| S-04 | Поиск задач | Ускоряет работу в больших проектах; для MVP с небольшим числом задач не обязателен. |
| S-05 | Фильтрация задач | Улучшает навигацию, но Backlog MVP показывает все задачи проекта. |
| S-06 | Calendar | Дополнительное представление; дедлайны уже видны в Backlog и на карточке. |
| S-07 | List/Table view | Альтернативное представление; Backlog покрывает базовую потребность просмотра. |
| S-08 | Сортировка таблицы | Зависит от S-07; вне обязательного состава. |
| S-09 | Цветовая индикация Epic | Визуальное улучшение; иерархия (M-17) работает и без цвета. |
| S-10 | Настраиваемые типы задач | В MVP тип выбирается из справочника `TaskType` (M-13); кастомизация — расширение. |
| S-11 | Базовые роли (руководитель/исполнитель) | M-24 даёт базовый контроль доступа; разграничение ролей — улучшение. |
| S-12 | История изменений задачи | Полезна для аудита; US-03 принимается без обязательной истории (фиксируется текущий статус). |
| S-13 | Real-time обновление Kanban (WebSockets/SSE) | Удобно, но US-03 не требует мгновенной синхронизации; участники видят изменения при обновлении доски. |

## 4. План разработки на семестр

### Сентябрь — фундамент

**Цель:** архитектура и связка клиент–сервер–БД.

- проектирование БД;
- пользователи, проекты, участники проектов;
- основные сущности задач, статусы, типы;
- JWT-аутентификация;
- основные REST-эндпоинты;
- структура Flutter-приложения, регистрация и авторизация, базовая навигация.

**Результат:** пользователь регистрируется, входит и создаёт проект.

### Октябрь — управление задачами

**Цель:** основная работа с задачами и командой.

- создание/просмотр/редактирование/удаление задач (US-01);
- назначение исполнителя, приоритет, дедлайн;
- изменение статуса;
- иерархия Epic → Task → Subtask;
- добавление участников проекта.

**Результат:** команда ведёт проект и работает с задачами.

### Ноябрь — визуализация

**Цель:** удобный просмотр и изменение состояния задач.

- Backlog (US-02);
- Kanban и смена статуса через Kanban (US-03);
- отображение исполнителя, приоритета, дедлайна.

**Результат:** пользователь просматривает задачи в Backlog и меняет статус
на Kanban; основной сценарий MVP проходит end-to-end.

### Декабрь — стабилизация и завершение MVP

**Цель:** стабильность, тестирование, документация, демонстрация.

- исправление критических ошибок, обработка ошибок, валидация, права доступа;
- тестирование REST API и основных пользовательских сценариев;
- интеграция frontend и backend;
- документация и подготовка демонстрации.

**Главный приоритет декабря** — не новые функции, а стабильность MVP.
Дополнительные функции (Should/Could) добавляются только при стабильной базе.

## 5. Основные сущности MVP

- `User` — пользователь;
- `Project` — проект;
- `ProjectMember` — участник проекта;
- `Task` — задача;
- `TaskType` — тип задачи;
- `Status` — статус задачи.

Иерархия задач реализуется связью между задачами: **Epic → Task → Subtask**.
Задачи связаны с проектом и исполнителем (`ProjectMember`).

## 6. AI как Post-MVP

AI — запланированная возможность Arij, но вынесена за границы MVP
(W-01…W-05). Сначала должны стать стабильными БД и REST API; после этого
агент сможет использовать готовые операции системы.

Предполагаемая архитектура (Post-MVP):

`Flutter Client` ──[ Prompt + JWT ]──> `AI Microservice (Gemma + MCP)` ──[ REST API + JWT ]──> `Arij Main Backend` ──> `PostgreSQL`

## 7. Сценарий демонстрации MVP

Сценарий подтверждает полезность MVP как **целостного пользовательского
результата** (исходная ситуация → действия → наблюдаемый результат).

**Исходная ситуация:** пользователь зарегистрирован, но не имеет проектов;
в системе есть второй зарегистрированный пользователь (будущий исполнитель).

**Действия:**

1. Пользователь входит в систему (M-02).
2. Создаёт проект «Arij» и становится его участником (M-05).
3. Добавляет второго пользователя в участники проекта (M-07).
4. Создаёт Epic «Авторизация» (M-08, M-17).
5. Создаёт Task «Падает сессия при логауте» с типом `Bug`, приоритетом `High`,
   исполнителем — вторым пользователем, дедлайном (US-01); задача получает
   уникальный номер (M-12).
6. Открывает Backlog и видит задачу со статусом, исполнителем, приоритетом
   и дедлайном (US-02).
7. Открывает Kanban, перемещает карточку задачи из «To Do» в «In Progress»
   (US-03).
8. Повторно открывает Backlog/Kanban — статус сохранён (N-04).

**Наблюдаемый полезный результат:** в проекте есть задача с исполнителем
и дедлайном, видимая в Backlog и Kanban; её статус изменён и сохранён —
команда может планировать и отслеживать работу в одном месте.

> Отдельно существующие интерфейс, база и сервер не являются результатом
> демонстрации; показывается сквозной пользовательский сценарий.

## 8. Критерии готовности MVP

MVP готов, когда реализован и проверен основной сценарий:

1. Пользователь регистрируется.
2. Пользователь входит в систему.
3. Пользователь создаёт проект.
4. Пользователь добавляет участников.
5. Пользователь создаёт задачу (US-01).
6. Задача получает уникальный номер (M-12).
7. Назначается исполнитель (M-14).
8. Устанавливается приоритет и дедлайн (M-13).
9. Изменяется статус (US-03).
10. Поддерживается структура Epic → Task → Subtask (M-17).
11. Задачи отображаются в Backlog (US-02).
12. Задачи отображаются на Kanban (M-19).
13. Изменения сохраняются в PostgreSQL (N-04).
14. Клиент взаимодействует с сервером через REST API (N-01).
15. Аутентификация — JWT (N-02).
16. Реализован базовый контроль доступа (M-24).
17. Основной сценарий работает от начала до конца.
18. Критические ошибки исправлены.
19. Основной функционал протестирован.

## 9. Итоговый scope MVP

### Must have

Авторизация и регистрация, пользователи, проекты, участники, задачи,
Epic/Task/Subtask, статусы, исполнители, приоритеты, дедлайны, Backlog,
Kanban, смена статуса через Kanban, REST API, PostgreSQL, JWT, базовый
контроль доступа, валидация, обработка ошибок. Подробно раскрыты:
**US-01, US-02, US-03**.

### Should have

Поиск, фильтрация, сортировка, Calendar, List/Table view, Drag & Drop,
базовые роли, история изменений, real-time обновление Kanban, цветовая
индикация Epic, настраиваемые типы задач.

### Could have

Reports, Timeline, расширенная аналитика, комментарии, уведомления,
вложения, пользовательские поля, гибкий workflow, расширенная ролевая
модель, тёмная тема.

### Won't have

AI-агент и интеграция LLM/MCP, полноценная мобильная версия, внешние
интеграции, сложная система разрешений, production-grade масштабирование.

Такой scope позволяет за один семестр сделать **не набор отдельных экранов,
а законченный основной сценарий командного трекера задач**. Состав MVP
согласован с таблицей MoSCoW и тремя подробными User Story; зависимости
US-01, US-02, US-03 покрыты элементами Must have (проект, участник,
задача, статус, Backlog, Kanban).
